## 3. 本轮代码改动

### 3.1 把静默的 ASSERT 变成可读的错误码（核心）

`mu_basecore/EmbeddedPkg/Library/PrePiLib/PrePiLib.c` 的 `LoadPeCoffImage()` 有四步，每步后面都是
`ASSERT_EFI_ERROR(Status)`；`AllocateCodePages()` 找不到 HOB 时是 `ASSERT (FALSE)`。DEBUG 构建下这些都是
`CpuDeadLoop` —— **失败即静默死机，不打印任何东西**。这正好解释了我们反复看到的"停在某一处、毫无信息"。

改为：失败时在屏幕上**画出该步的标签色 + `EFI_STATUS` 的位图**，然后 `return`（不再死循环，启动得以继续）：

| 标签位置 | 颜色 | 对应调用 |
|---|---|---|
| 1290 | 灰 | `FfsFindSectionDataWithHook`（取 PE32 段） |
| 1300 | 红 | `PeCoffLoaderGetImageInfo` |
| 1312 | 橙 | `AllocateCodePages` / `AllocatePages` |
| 1324 | 黄 | `PeCoffLoaderLoadImage` |
| 1336 | 绿 | `PeCoffLoaderRelocateImage` |
| 1348 | 青 | 四步全过（含 `InvalidateInstructionCacheRange`） |
| 1360 | 品红 | `FfsGetFileInfo` |

`EFI_STATUS` 位图：行 **1400 + i*12**（i=0..15）画低 16 位（**白=1，深灰=0**，位 0 在最上），
行 **1600** 画 bit63（EFI 错误位）。**拍一张照片即可解出确切错误码。**

配套：调用方 `LoadDxeCoreFromFfsFile` 的 `ASSERT_EFI_ERROR` 也改成"画状态 + 返回"，并保留 1154/1160 两条
进度带，从而把"PE32 到手 → 进 DxeMain"这段**切成可判读的三段**。

### 3.2 其余固件修正（此前已做，本轮复核确认）

- **SEC 对齐真机端口 umi**：删 `CheckHobList()` 整个函数、删 `RamLogReset()`、用
  `ProcessLibraryConstructorList()` 取代手写的 4 个构造函数。这三处让固件从"HOB 尾部卡死"推进到"能进 DXE 装载"。
- **`Display Reserved` 属性改回 `WRITE_THROUGH_XN`**（与 umi、与 wh1stl3 的表逐字相同）。
- **`[uefi_fd]`、`PcdSystemMemoryBase`、`PcdCPUCoresStackBase/Size`、`PcdFrameBufferWidth/Height`**
  与 wh1stl3 的表逐条一致（1600×2560）。
- **我们的内存表与 wh1stl3 的 45 行逐条相同**（含 `Display Reserved 0x9C000000+0x2400000`、
  `UEFI FD 0x9FC00000+0x300000`、`UEFI Stack 0x9FF90000+0x40000`）。

## 4. 离线证据：固件卷结构完好

用自写解析器拆了本轮产出的 `SILICIUM_UEFI.fd`（3,145,728 B）：

```
FVMAIN_COMPACT (0x300000)
  ├─ FFS FREEFORM 69,560 B          (Sec)
  └─ FFS FV_IMAGE 999,634 B
       └─ GUIDED (LZMA, lc=3 lp=0 pb=2 dict=16MiB)
            → FVMAIN 6,139,904 B
                 FREEFORM ×61, DRIVER ×37, APP ×6, DXE_CORE ×1
DXE_CORE @0x280: PE32+ / machine=0xAA64(AARCH64) / 5 sections
                 SizeOfImage=192,512  EntryPoint=0x123C
```

**结论：DxeCore 的 PE 镜像完整、可解析。** 所以失败发生在运行期（装载/重定位/跳转），不是镜像损坏。
这也排除了"FV 缺 DxeCore""PE 被压缩破坏"这类猜测。

## 5. 顺带确认的几件事（避免重复排查）

| 疑点 | 结论 |
|---|---|
| `CacheMaintenanceLib` 用了空实现（会 `ASSERT(FALSE)`）？ | ❌ 不是。平台映射到 `ArmPkg/Library/ArmCacheMaintenanceLib`（真实现） |
| 平台没 include `KonaPkg.dsc.inc`？ | ❌ 有（我们的 `enuma.dsc:51`） |
| `APSS_HM` 缺失导致看门狗没关？ | ❌ 表里有该行 |
| 内存表与第三方不一致？ | ❌ 45 行逐条相同 |
| 调试掩码把输出过滤了？ | 部分是：`PcdDebugPrintErrorLevel = 0x8007EE0F`，**包含 `DEBUG_LOAD`**，所以 `LoadDxeCoreFromFfsFile` 里那句 `DEBUG("Loading DxeCore at ...")` 会执行（它落在此前的观测死区里） |
| 帧缓冲控制台在 MMU 后失效的原因 | 未定论。`SerialPortWrite()` 每次都会对 `Pitch×Height`（我们=15.6 MB）做一次 cache 回写/失效，并重读 `mFbGeometry` 交接结构；但它**不会**造成死循环——固件在它之后仍继续推进（色带为证）。umi 用 `UMI_SKIP_EARLY_FRAMEBUFFER`、wh1stl3 直接把 `SerialPortLib` 设成 Null，都在绕开这条路径 |

## 6. 下一次实机只需一次，就能分三路

烧 `/tmp/enuma-status.img`（`boot.img` sha256 `2d11b85b5c0306a0178c256e63f25ad29228cbbe307b76bad5384f6907f748f8`），拍照：

| 现象 | 结论 | 下一步 |
|---|---|---|
| 1154 **红** + 某个标签色 + 位图 | `LoadPeCoffImage` 某步失败，**位图就是确切状态码** | 按状态码定位（如 `EFI_LOAD_ERROR`/`EFI_COMPROMISED_DATA`/`EFI_OUT_OF_RESOURCES`） |
| 1154 **绿** 但没有 1160（青） | PE32→DxeMain 之间，即 `BuildModuleHob` 或那句 `DEBUG` | 去掉该 DEBUG、给 `BuildModuleHob` 加带 |
| 1160 **青** 但没有 1180（白） | 已到 `GetHobList()`，问题在跳转/入口 | 检查 `SwitchStack`/入口点 |
| 1180 **白** 或更高 | **DxeMain 进了** | 直奔 DXE 派发与菜单 |
